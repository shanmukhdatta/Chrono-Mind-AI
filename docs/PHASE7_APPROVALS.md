# Durable planning approvals — preview/propose/approve/reject/undo

Authenticated API routes:
- POST /api/v2/plans with `{"days":7}` — snapshot tasks and proposed blocks; no calendar writes.
- GET /api/v2/plans, GET /api/v2/plans/{id} — review pending and historical plans.
- POST /api/v2/plans/{id}/approve — explicit authenticated approval, conflict and preference recheck, PostgreSQL transaction.
- POST /api/v2/plans/{id}/reject — reject without a calendar write.
- POST /api/v2/plans/{id}/undo — remove intact blocks generated by that plan; fails if those blocks changed.

**Critical safety:** The proposal stores exact task versions; approval locks the owner row and affected task rows, rechecks events, existing work, effort caps, deadlines, break spacing and preference snapshot. SQLAlchemy commits created blocks and approved status together. Use real PostgreSQL for concurrency acceptance; SQLite mocks do not demonstrate cross-process guarantees. The current task PATCH route may still alter scheduled tasks after approval, so **do not yet claim complete concurrency safety or production readiness**.

Proposal expiry is one hour. Preview starts close to wall-clock time; old proposals with a passed start must be regenerated. No automatic approval or destructive task deletion.

The approval UI and LangGraph checkpointed orchestration are future PRs. Production migrations require DBA/operator review and backups.
